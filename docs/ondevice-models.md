# On-device models (Gemma 4 E2B and EmbeddingGemma 2)

Shared package: `io.github.daddymean.agentickeyboard.models` (Hax, draft #209).

- **Catalog** — `ModelCatalog`. EmbeddingGemma 2 (twin memory) and Gemma 4 E2B (keyboard rewrite) are both pinned (URL to a Hugging Face commit, SHA-256, exact byte size).
- **Manager** — `ModelManager` / `ModelConsent` / `ModelBytesFetcher`. Download only after an explicit opt-in (default off). SHA-256 is verified; a mismatch deletes the file (see Download reliability below). Storage is `noBackupFilesDir/models/`. `ModelManager.forApp(context)` is the production wiring.
- **Keyboard routing** — Nano if available and allowed (`BACKGROUND_USE_BLOCKED` / `BUSY` fall through), then local Gemma 4 E2B if opted in, the file is ready, and the device is supported (arm64/x86_64 and at least 6 GB RAM). Rewrite prefers Gemma when it is eligible and falls back to the ML Kit rewriter; a 20s timeout that races a dedicated single-thread worker (blocking native initialize/sendMessage cannot be cancelled, so a hang still returns to ML Kit and late results are discarded; a busy engine is skipped until the stuck call finishes), init/inference exceptions, a missing or corrupt model, or an unsupported/low-RAM device all take that ML Kit path. If ML Kit also fails after an engine was attempted, the keyboard shows a fixed "On-device rewrite is unavailable" state instead of a silent no-op. Otherwise existing heuristics run. No silent cloud fallback. Password, OTP, payment and incognito fields are blocked by `EditorPrivacy` and `TwinPrivacyFilter`.
- **Runtime** — LiteRT-LM `com.google.ai.edge.litertlm:litertlm-android:0.19.1` (Apache-2.0). The AAR ships Kotlin 2.4 metadata and Java 21 bytecode; this repo stays on Kotlin 2.2.10 and Java 11. Calls go through Java reflection (`LiteRtGemmaEngine`, and `LiteRtTextEmbedder` in #209) plus `-Xskip-metadata-version-check` and R8 keep rules. Do not import `com.google.ai.edge.litertlm` from Kotlin. GPU backend with CPU fallback for Gemma.
- **Keyboard extras** — the settings UI shows the size before download and uses Wi-Fi by default (`ModelDownloadPolicy`). Turning the toggle off does not delete the 2.59 GB file; Delete does, via `ModelManager.setOptedIn(spec, false)`.

See also `docs/twin-embedding-search.md` in #209 for the manager API.

## Download reliability (KEYBOARD-049)

Before: one request streamed into `<file>.tmp`; any failure (Wi-Fi drop, process kill, timeout) deleted the temp file and the next try restarted from byte 0, which for the 2.59 GB Gemma file wastes everything already received. The 5-minute read timeout also meant a stalled connection hung for minutes. Progress was never reported (`Downloading(0, total)` stayed at 0%), "Verifying" was never shown, and the file was hashed again on every `isReady()` call.

Now:
- **Resume.** `OkHttpModelFetcher` (a `ResumableModelFetcher`) writes to `<file>.part` and, when bytes already exist, asks for `Range: bytes=N-`. It accepts a `206` only when `Content-Range` starts exactly at N, rewrites from 0 if the server answers `200`, and discards the partial on `416` or a wrong range. Hugging Face's `resolve/` URL answers Range with `206` through the same redirect the old code already followed (checked for both pinned URLs).
- **Retry.** `ModelManager.download` retries network failures and HTTP 408/429/5xx up to four times in a row without progress (2, 5, 15, 30 s pauses; any progress resets the count). HTTP 4xx (404, 403) is not retried. After the retries the `.part` file is kept, so the user's next tap continues from the same byte.
- **Trust.** `<file>.part.meta` holds URL + SHA-256 + size; a partial from another pin is never continued. A hash mismatch after a *resumed* download is retried once from byte 0 before it is reported; a mismatch on a fresh download still deletes everything and reports `HashMismatch`. Only a SHA-256-verified file is ever renamed into place.
- **Disk space.** The remaining bytes are checked against free storage first, so the user gets a clear message instead of a late write failure.
- **Progress.** The fetcher reports bytes at most every 1 MB or 250 ms. `LocalGemmaController` turns that into `Downloading(bytes, total)` and then `Verifying`; the settings screen shows MB/GB, "Resume on Wi-Fi" when a partial exists, and a resume hint after a failure. The EmbeddingGemma button on the twin screen shows the same progress.
- **Verification cost.** `verifiedFile`/`isReady` remember a positive hash result per process (keyed by path, size, modified time and pin), so the settings screen no longer re-hashes 2.59 GB on every recomposition. A changed file is hashed again. The hash buffer is 256 KB and the write buffer 256 KB (OkHttp hands out 8 KB reads).
- **Unchanged:** opt-in, size acknowledgement, Wi-Fi-by-default policy, SHA-256 pins, URLs and hosts, no new permission, no new dependency, no telemetry. Nothing about the user's text is read or logged; error messages carry only an HTTP status or exception text.

Options not done (each needs Keith's call):
1. **Background download that survives the app being closed** (WorkManager `CoroutineWorker` or a foreground service): `work-runtime-ktx` is already in the version catalog (Apache-2.0) but not used by `:app`; a foreground service would need `FOREGROUND_SERVICE` (+ `POST_NOTIFICATIONS`) permissions, which are Keith's sign-off. It would also start work without an explicit tap after opt-in, which `ModelDownloadPolicy` currently forbids.
2. **Parallel range chunks** (e.g. 3-4 connections per file). Helps only when one connection is throttled below the line rate; adds code, a part-map and more CDN load. Measure on the phone first.
3. **Hash while downloading** to avoid the separate 2.59 GB SHA-256 pass at the end (needs the digest state to survive resume, or a re-hash of the prefix on resume).
4. **A one-time "essential first" bundle:** the two models are independent opt-ins and nothing downloads on first run by itself, so the order is already the user's choice. If Keith wants a first-run flow, fetch EmbeddingGemma (165 MB) first and offer Gemma (2.59 GB) after.
5. **Network-change auto-resume** (ConnectivityManager callback) so a paused download restarts when Wi-Fi returns; needs only `ACCESS_NETWORK_STATE`, which the manifest already declares.
